# 万首有效音频与本地索引性能验收

2026-10-08。正式本地扫描、标签读取、索引保存/恢复、增量刷新及实际 WinUI 列表联合验收，20 项条件全部通过。当前验证版仍为 [preview.13](PREVIEW13_ACCEPTANCE.md)；本阶段增加 Debug 验收入口，没有改写固定交付包或改变生产行为。

## 样本与测量

独立测试目录下 100 个子目录，每目录 100 个文件，共 10000 份有效音频。由现有 FFmpeg 编码五段 2 秒、48 kHz 双声道的 WAV/FLAC/MP3/Opus/M4A，每种复制 2000 份，写入标题、歌手及专辑标签。所有文件经过正式 `LocalMusicMetadataReader`，不用占位文件或受控标签读取器代替。引用按目录相对路径独立，全部时长与三项标签检查通过。

| 步骤 | 实测耗时 |
| --- | ---: |
| 生成有效副本 | 4.38 秒 |
| 初次扫描与 10000 次标签读取 | 85.70 秒 |
| 保存完整索引 | 55 毫秒 |
| 新存储实例恢复完整索引 | 50 毫秒 |
| 未变化目录刷新，零标签重读 | 366 毫秒 |
| 单文件修改时间变化，仅重读一个文件 | 399 毫秒 |
| 缓存来源挂载并首次布局 | 205 毫秒 |
| 四次滚动至第 1001/5001/10000/1 行 | 630 毫秒 |
| 从万首队列末行开始实际播放推进 | 788 毫秒 |
| 缓存歌手搜索，返回 2000 项 | 15 毫秒 |

首次布局和滚动测量包含每次人为等待 150 毫秒，用于等待布局稳定；不作为帧率或纯渲染时间。索引恢复在同一进程创建新的存储实例，未清除系统文件缓存，不等于整个应用冷启动。此前 [两进程启动索引验收](NATIVE_LOCAL_INDEX.md) 已分别验证后台暂停时缓存先显示、真实播放及来源保持。

进程私有内存依次为生成前 99.9 MiB、初扫后 202.7 MiB、恢复后 209.4 MiB、未变刷新后 204.4 MiB、窗口搜索/播放后 238.2 MiB。本次同时保留扫描/恢复/刷新快照以检查身份，未强制 GC；这些是阶段快照，不证明长期内存泄漏或连续运行曲线已完成。

## 一致性与窗口检查

- 持久索引恢复全部曲名、歌手、专辑、时长及来源引用，顺序保持。修改单文件时间只触发一次标签读取，所有身份保持。
- 第 5000 项时取消刷新，原万首快照及已保存索引字节保持；第 10001 个有效文件明确超限拒绝，原索引仍可恢复万首。
- 正式所有音乐页面挂载 10000 行，无下一页；实际 `ItemsStackPanel` 已创建容器少于 80 个，四处滚动的目标行均可见，滚动范围与 10000×64 DIP 一致。
- 正式播放入口从末行建立完整万首队列，NativeMusicPlayer 静音播放实际走时后暂停；搜索返回全部 2000 个 MP3 歌手条目，保持现有队列和播放流，清空搜索恢复万首，停止释放流。
- 全程使用独立 synthetic-settings；不登录、写入 NAS、扫描用户音乐或修改正式配置。运行结束正常关闭自建进程，按记录的自有文件和空目录清理，cleanup=true。

## 复现与证据

Debug 应用：`FnMusic.App.exe --preview-synthetic --verify-local-scale-window`。需要现有 FFmpeg 命令行编码器、至少 1 GiB 可用空间；生成样本仅用于自有测试目录。入口及验证实现均在 `#if DEBUG` 内，不进入 Release。
